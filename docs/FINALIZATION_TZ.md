# Техническое задание: подготовка сайта расписания к эксплуатации

## Цель

Оставить один рабочий продукт — локальный веб-сайт с C++/OR-Tools backend. Пользователь должен через браузер загрузить учебную нагрузку и фактически проведённые занятия, настроить ограничения, проверить данные, запустить решатель, проверить результат и опубликовать расписание без ручного редактирования JSON и запуска вспомогательных скриптов.

## Источники данных

- Файл «Вклейки 2026-2027» задаёт семестровую нагрузку: группа, дисциплина, подгруппа, преподаватель и часы.
- Таблицы готового расписания задают подтверждённый факт проведения занятий. Одна пара равна двум академическим часам.
- «Классный час» при импорте факта пропускается и не уменьшает остаток учебной нагрузки.
- Повторный импорт того же периода заменяет подтверждённые записи этих дат и не создаёт двойной учёт.

## Функциональные требования

1. Импорт нагрузки должен сохранять постоянные идентификаторы, ограничения преподавателей, требования к кабинетам и уже подтверждённый факт.
2. Импорт проведённых занятий должен сопоставлять группу, дисциплину, подгруппу и преподавателя с нагрузкой. Неоднозначные и не найденные строки должны блокировать применение и показываться пользователю.
3. Учёт часов должен отдельно показывать семестровый план, подтверждённый факт, проект текущего расписания и остаток.
4. Дедлайн вычитки задаётся точной датой; для текущего семестра — 19.12.2026.
5. Перед генерацией backend рассчитывает остаток по подтверждённому факту и минимальную нагрузку текущего периода. Эти требования становятся ограничениями модели, а не только предупреждениями интерфейса.
6. Интерфейс должен позволять задавать рабочие дни и пары, исключения по датам, минимальную нагрузку по датам и срокам, предельную дневную/недельную нагрузку, требования к кабинету и допустимые начала двухпарных блоков.
7. Финальный результат должен проходить backend-валидацию конфликтов групп, преподавателей, кабинетов, окон, блоков и квот до публикации.
8. История изменений базы и откат сохраняются для всех импортов и настроек.

## Нефункциональные требования

- Единственный поддерживаемый пользовательский интерфейс — сайт; Electron/desktop-сборка удаляется.
- Backend слушает только `127.0.0.1` по умолчанию и отдаёт API; frontend работает через тот же origin в production и через Vite proxy в разработке.
- Ошибка импорта или генерации не заменяет действующую базу или последнее проверенное расписание.
- Все массовые изменения проверяются автоматическими тестами и контрольным запуском сайта.

## Критерии приёмки

- Новые «вклейки» загружаются через сайт и отражаются в группах, занятиях и учёте часов.
- Две предоставленные таблицы расписания импортируются как факт за 02–08.09.2026; классные часы отсутствуют в зачтённых часах.
- Отчёт вычитки строится до 19.12.2026 и перечисляет преподавателей с риском нехватки доступных пар.
- Настройки ограничений проходят полный путь: форма → API → JSON → модель/валидатор.
- Сайт собирается, backend компилируется, API и ключевые пользовательские сценарии проходят smoke-тест.
- В проекте нет Electron-кода, установщика и `build-desktop`.
