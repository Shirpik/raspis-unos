# Аудит приложения расписания — 5 сентября 2026

## Главный вывод

Текущий продукт умеет раскладывать заранее выбранные квоты и проверять многие ограничения расписания. Однако он пока **не обеспечивает непрерывный контроль вычитки всего учебного плана до срока**. Успешная проверка 349 размещений не доказывает ни максимальную нагрузку, ни выполнимость семестрового плана.

Причина недогруза Гарбузова и Меренчукова установлена: при увеличении субботней нагрузки Ханьжиной отдельный скрипт уменьшил их квоты, затем подогнал под уменьшенные квоты контрольные минимумы. Это ошибка предыдущей подготовки данных, а не потеря пар при отображении.

Аудит не изменял рабочую базу, расписание, код приложения или установщик. Диагностические серверы и проверки выполнялись на копиях в `.tmp`. Добавлен этот отчёт. Существовавший до аудита `output/latest/strict_audit.json` оставлен без изменений.

## Проверенная область и ограничения аудита

Проверены основные цепочки: Vue-формы и API-клиент → JSON-хранилище → подготовка квот → C++/OR-Tools → распределение кабинетов → валидатор → общие/групповые результаты → отображение и Excel; отдельно учёт часов, импорт вклеек, календарные исключения, desktop-обновление и альтернативный сервер `deploy/demo-server.mjs`.

Исходное состояние: ветка `main`, база `data/timetable_data.json`, период 04–05.09.2026, расписание `output/latest/schedule_all.json`. Проверки C++ выполнялись исполняемыми файлами `build/Release`. Результаты относятся к этому checkout и данным; установленная у пользователя копия приложения, удалённый сайт и все варианты сборок отдельно не сертифицированы. Аудит не является доказательством отсутствия любых ошибок и не включает полноценный security/pentest или визуальный обход каждой страницы.

## 2. Критические и существенные находки

### A01 — P1. Контрольные минимумы меняются вслед за результатом

Описанная выше подмена целей позволяет получить «всё выполнено» после снятия обязательных пар. Аналогичный пересчёт целей есть в `apply_absence_revision_20260903.py`. Смысл `minimum_safe_for_deadline` дополнительно ослабляется через `min(selected, previous)`.

**Исправление:** отделить согласованный минимум, рекомендуемый темп и результат оптимизации. Минимум не должен автоматически уменьшаться при подборе квот. Любое ослабление — отдельное решение с причиной и показанным недобором.

**Приёмка:** попытка снять пару ниже согласованного минимума не получает зелёный статус; указывает преподавателя, дату/период, недобор и причину.

### A02 — P1. Учёт часов занижает полный план и не является журналом вычитки

[BuildHoursReport](C:/Users/Student/Desktop/raspis-unos/src/data_store.cpp:1643) обнуляет план при `plan_active=false`. Подготовительные скрипты используют этот флаг для занятий, не выбранных на текущие два дня, хотя семестровые часы у них остаются.

Подтверждено настоящим `/api/hours` на копии базы:

| Преподаватель | Сумма `total_hours` всех его строк в базе | «План» API | «Поставлено» API |
|---|---:|---:|---:|
| Меренчуков | 1260 ч | 594 ч | 26 ч |
| Гарбузов | 1272 ч, включая 72 ч УП | 496 ч | 24 ч |
| Ханьжина | 168 ч | 66 ч | 16 ч |

Кроме того, [API](C:/Users/Student/Desktop/raspis-unos/src/http_server.cpp:1436) считает часы только из `output/latest/schedule_all.json`. Архив предыдущих периодов не является источником накопленного факта. При замене `latest` другим периодом предыдущие размещения исчезнут из расчёта. Поставленные занятия сразу попадают в `credited_hours`, даже если ещё не проведены.

**Исправление:** раздельные сущности «учебный план», «квоты периода», «запланированные события», «подтверждённо проведённые события». Не исключать обязательные часы из семестрового плана из-за отсутствия пары в этой субботе. Сохранять журнал факта со стабильными идентификаторами и защитой от двойного зачёта при повторной генерации.

**Приёмка:** переключение периода и повторная генерация не меняют уже подтверждённый факт; выключение занятия из генерации не уменьшает семестровый долг.

**Исправление:** жёсткое правило с датой начала действия, общее для модели, распределителя комнат и валидатора. Лучше хранить правила по стабильным UID в данных, а не числовым ID внутри C++.

**Приёмка:** отрицательный тест с 207 отклоняется; правильный ЦПДЭ проходит; утверждённая пятница сохраняется как исторический снимок.

**Исправление:** единый неизменяемый снимок результата, `generation_id` и хеш входных данных/правил; все производные выгрузки строятся из него и заменяются атомарно. Запретить ручное продвижение только `schedule_all.json`.

**Приёмка:** полное совпадение событий общего файла, групп, преподавателей, API и Excel; отчёт от другой генерации отклоняется.
