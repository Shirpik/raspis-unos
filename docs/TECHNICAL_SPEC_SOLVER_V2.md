# Техническое задание: решатель расписания v2

## 1. Цель

Повысить скорость, управляемость и объяснимость генерации расписания без ослабления обязательных ограничений и без риска повреждения уже опубликованного расписания.

## 2. Исходные условия

- учебный период разбит на независимые недельные CP-SAT задачи;
- нагрузка дисциплин распределяется по неделям квотами;
- в рабочем наборе около 46 групп и 987 занятий;
- на компьютере 6 физических / 12 логических ядер и около 16 ГБ RAM;
- измеренный оптимум для одного экземпляра CP-SAT — 4 worker-потока;
- первое допустимое решение реальной недели находится примерно за 4,5 секунды;
- отдельная фаза качества должна улучшать окна ограниченное время.

## 3. Приоритет P0 — надёжность и обратная связь

### 3.1. Отмена внутри CP-SAT

Требование: `POST /api/schedule/cancel` должен останавливать текущую фазу solver, а не ждать окончания недельного лимита.

Критерии приёмки:

- флаг отмены подключён к TimeLimit feasibility- и quality-фазы;
- повторный relaxed-запуск после отмены не выполняется;
- состояние API становится `cancelled`;
- уже решённые недели остаются доступными как частичный результат.

### 3.2. Недельный preflight

До запуска CP-SAT проверить:

- вместимость недели для каждой подгруппы;
- физическую вместимость недели для каждого преподавателя;
- число возможных позиций для каждого занятия;
- загрузку закреплённых аудиторий;
- сохранение полной суммы квот дисциплины.

Результат сохранять в `output/latest/solver_preflight.json` и отдавать через `GET /api/schedule/preflight`.

Критерии приёмки:

- критическая ошибка блокирует генерацию до построения CP-SAT;
- каждая ошибка содержит неделю, сущность, код и понятное сообщение;
- корректная фиктивная сетка проходит preflight.

## 4. Приоритет P1 — управляемая скорость

Добавить профили:

- `fast`: только первое допустимое решение;
- `balanced`: допустимое решение + 5 секунд улучшения окон;
- `final`: допустимое решение + 30 секунд финальной вычитки, включая окна преподавателей.

API:

- `GET /api/settings/solver-profiles`;
- `POST /api/settings/solver-profile/{fast|balanced|final}`.

Критерии приёмки:

- профиль сохраняется в версии данных;
- неизвестный профиль возвращает HTTP 404;
- изменения видны через `GET /api/settings/solver-config`.

## 5. Приоритет P1 — измеримость

Для каждой недели сохранять:

- время построения модели;
- время feasibility- и quality-фаз;
- число переменных и ограничений;
- branches, conflicts и число warm-start hints;
- статус preflight и итоговый статус недели.

Отчёт доступен через `GET /api/schedule/solver-metrics`.

## 6. Приоритет P2 — параллельные недели

Недели после расчёта квот независимы и могут решаться параллельно. Реализация допускается только за настройкой `parallel_week_jobs` со значением по умолчанию `1`.

Перед включением значения `2` необходимо подтвердить:

- потребление RAM не превышает заданный лимит;
- результаты с одинаковым random seed воспроизводимы;
- автосохранение выполняется только в управляющем потоке;
- callbacks корректно показывают несколько активных недель;
- ускорение на полном наборе не меньше 20%.

До выполнения этих критериев production-режим остаётся последовательным.

## 7. Приоритет P2 — улучшение квот

Если недельный preflight выявляет локальную перегрузку, квоты следует перебалансировать между соседними разрешёнными неделями, сохраняя:

- полную нагрузку дисциплины;
- чётность недели;
- недоступность группы;
- зафиксированные занятия;
- минимальное отклонение от равномерного распределения.

Автоматическая перебалансировка не должна молча менять нагрузку: изменения записываются в диагностический отчёт.

## 8. Общие критерии готовности

- production-сборка успешна;
- изолированный CTest проходит;
- текущий файл данных не изменён тестами;
- опубликованное расписание не перезаписывается до явной публикации;
- API после сборки запущен локально на порту 8080.
